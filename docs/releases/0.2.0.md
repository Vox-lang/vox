# Vox 0.2.0 — calling a library from Vox

In 0.1.x you could build a shared library with `--shared`, but only a C or
assembly caller could reach it — the `.so` was a dead end from Vox. 0.2.0
closes that gap. A Vox program now calls a Vox library: you build one with
`--shared`, another program consumes it with `see`, and the compiler
type-checks the call across the boundary. That is the release.

## Writing a library

A library is a `.vox` file that opens with a `Library` declaration and is built
with `--shared`:

```vox
Library mathkit version "1.0".

To 'add two numbers' with a number called x and a number called y. Return a number, x add y.

To greet.
  Print "hello from mathkit".
```

```bash
$ vox mathkit_lib.vox --shared -o libmathkit.so
$ nm -D --defined-only libmathkit.so
00000000000005c4 T mathkit_1_0_add_two_numbers
00000000000005f9 T mathkit_1_0_greet
```

Two files come out: `libmathkit.so`, the library itself, and `libmathkit.lib`
beside it. The names in `nm -D` are mangled — `mathkit_1_0_add_two_numbers`,
not `add two numbers` — so two versions of one library can live in the same
`.so` without colliding. More on that under Versioning.

A shared library has no entry point, so only function definitions, `Library`,
and `see` may appear at the top level; a stray top-level `Print` is rejected.
The library carries its own copy of the runtime, so it can use the full
language — lists, maps, files, floats — not a stripped subset.

## Using one

Build the library first, then `see` its `.lib` from another program:

```vox
see mathkit version "1.0" from "./libmathkit.lib".

a number called sum is 'add two numbers' of 3 and 4.
Print the sum.
```

```bash
$ vox consumer.vox -o consumer && ./consumer
7
```

That is the whole consumption path. The `see` names the library and version
and points at the `.lib` — not the `.so`. After that, `add two numbers` is
just a function: it type-checks like any other, and the call links the `.so`
in.

## The `.lib` file

The `.lib` is the interface to the library — its name and version, where its
`.so` is, and a table of contents of every exported function's signature:

```text
Library mathkit version "1.0".
Location "./libmathkit.so".

Table of Contents:
    To 'add two numbers' with a number called x and a number called y, returning a number.
    greet.
```

It exists because a `.so` carries symbol names but no Vox types. The compiler
cannot open a binary and read a signature out of it, so it reads the `.lib`
instead — that is where the types live. When you `see` a `.lib`, the compiler
checks every signature it promises against the `.so`'s actual exports,
registers the types so your calls check, and links the `.so`. You consume the
`.lib`; the `.so` is linked, never read for types.

## Versioning

Build two versions of one library into a single `.so`:

```bash
$ vox mathkit_lib.vox mathkit_v2.vox --shared -o libmathkit.so
$ nm -D --defined-only libmathkit.so
00000000000005c4 T mathkit_1_0_add_two_numbers
00000000000005f9 T mathkit_1_0_greet
0000000000000639 T mathkit_2_0_add_two_numbers
```

Both symbols are present and independently callable. A consumer pins a
version with `see`, and the version it pins keeps working after the other
ships beside it:

```bash
$ vox consumer_v1.vox -o c1 && ./c1   # see "mathkit" version "1.0"
7
$ vox consumer_v2.vox -o c2 && ./c2   # see "mathkit" version "2.0"
11
```

That is the point of the mangling: you can ship `mathkit` 2.0 without
breaking a program that still calls 1.0. Both link the same `.so`; neither
recompiles when the other version appears.

## The errors you will hit

A `.lib` and its `.so` can drift if you rebuild one without the other. The
compiler catches it at compile time, not at runtime. Ask for a version the
`.lib` does not offer:

```text
Error: 'libmathkit.lib' has library "mathkit" but not version "1.5".
The available versions are: "1.0", "2.0".
```

Or a `.lib` that promises a function the `.so` no longer exports — a stale
interface:

```text
Error: the .lib entry 'To "ghost function" ...' promises the symbol 'mathkit_1_0_ghost_function', but 'libmathkit.so' does not export it (not in .dynsym).
The .lib is stale: it does not match the library binary. Rebuild the library with `vox --shared` to regenerate the pair.
```

Both name the file and what was expected. Knowing an error exists is what
stops it being frightening.

## If you call a library from C or assembly

This is the breaking part of 0.2.0. Every exported symbol is now mangled to
`<library>_<version>_<function>`, with no unmangled alias — so a C or
assembly caller that linked `add_two_numbers` must switch to
`mathkit_1_0_add_two_numbers` and relink. `--shared` also now requires the
`Library` declaration, and three old `see` forms that pointed at a `.so`
directly are compile errors. The full list, with the before/after, is in
`CHANGELOG.md`.

## What is not there

`see` of a `.so` is an error by design — a `.so` has no types to check
against, so the compiler sends you to the `.lib`:

```text
error: see of a .so is not supported. A .so is a binary; consume it through its .lib interface file.
  Canonical form: see '<lib>' version "<x.y>" from "<path>.lib".
```

There is also no qualification syntax for picking one library when two export
the same function name. If you `see` two versions of `mathkit` and call
`add two numbers`, the call is ambiguous, and the compiler names both:

```text
error: Call to 'add two numbers' is ambiguous: it is exported by library "mathkit" version "1.0" and library "mathkit" version "2.0". Vox never picks one by import order or by highest version — resolve it by defining a local 'add two numbers' (which shadows the imports, with a warning), or by renaming one library's export.
```

Pin one version with `see`, or rename one export. The reference for all of
this is the "Shared libraries" section of `LANGUAGE.md`.

## What else is new since 0.1.21

0.2.0 is the first release with an announcement; the changes from 0.1.21
through 0.1.24 were never written up. The rest, in the order you would meet
it.

### Collections

Lists grew into a real collection type. `Print` on a list now renders the
whole list:

```vox
a list called nums is [1, 2, 3].
Print the nums.
```
```
[1, 2, 3]
```

A list may hold mixed types — number, text, decimal, boolean — and each
element keeps its own type, so it reads back as what it is:

```vox
a list called m is [1, "two", 3.5, yes].
For each item in m, Print the item.
```
```
1
two
3.5
1
```

The compiler earns a statically-typed fast path by proof: a list it can prove
homogeneous stays untagged, and one it cannot prove widens to mixed by
default. That inference used to assume homogeneity and occasionally mis-tag a
slot, silently reinterpreting a value; it now widens when unsure, so an
opaque value is read back as what it is, not what the compiler guessed. A
list element may be a list, and printing is recursive —
`[1, [2, 3], "four"]` prints as written.

Two things make mixed lists programmable. Type predicates ask what a slot
holds:

```vox
a list called m is [1, "two", 3.5, yes].
For each item in m,
  if item is a text, Print "text: {item}",
  otherwise if item is a decimal, Print "decimal: {item}",
  otherwise if item is a boolean, Print "boolean: {item}",
  otherwise Print "number: {item}".
```
```
number: 1
text: two
decimal: 3.5
boolean: 1
```

And the `value` type carries a slot's tag across a function call, so one
function can take "whatever this is" and ask inside:

```vox
To describe with a value called item.
  If item is a number, Print "number".
  Otherwise if item is a text, Print "text".
  Otherwise Print "decimal".

a list called m is [1, "two", 3.5].
For each item in m,
  describe of item.
```
```
number
text
decimal
```

There is also a `nothing` value — the absent value, like null — which can sit
in a list, a map, or a `value` slot, prints as `nothing`, and is tested with
`is nothing`. It is not `0`: `0 is nothing` is false.

### Maps

A map is a key/value collection — a JSON object:

```vox
a map called person is {"name": "Ada", "age": 36}.
Print the person.
Print person's "name".
```
```
{"name": "Ada", "age": 36}
Ada
```

Read by key with `map's "key"`, set with `set map's "key" to value`, iterate
with `keys` / `values`. A missing key sets the error flag — it is an error,
not `nothing` — so "the key is absent" stays distinct from "the key holds
nothing".

Maps now own their keys: the map copies each key on insert rather than
borrowing the caller's text. No current Vox program could break the old
borrowing — keys are text literals and buffers are rejected as keys — but a
dynamic key would have, so this is a correctness fix ahead of the JSON
parser, not a symptom anyone hit.

### Arithmetic and `nothing`

Arithmetic operands are now type-checked. Using a non-numeric value in
arithmetic is a compile error with a cast suggestion — code that used to
compile to a wrong number now stops and tells you how to convert:

```text
error: Cannot use text s in arithmetic; cast it first with 'as a number' or 'as a float'.
```

`nothing` is refused the same way: `5 add nothing` is a compile error
pointing at `is nothing`, and a `nothing` that turns up at run time (read
from a map or a mixed list) sets the error flag so `on error` catches it.
`nothing` is new in this range, so this is a safe default, not a change to
code that used to work — there was no `nothing` to put in arithmetic before.

### `.vox` is the sole source extension

The compiler reads one source extension, `.vox`. The main input still
accepts any file regardless of extension, but `see` of a `.vox` source now
inlines correctly. It used to be silently skipped — the include gate matched
`.en` — so `see "./utils.vox".` compiled while pulling in nothing and the
call site errored "Unknown function". The `.en` form, which was the one that
worked, no longer inlines. If a `see` stopped working on upgrade, point it
at a `.vox`.

### Compiler fixes (0.1.24)

Three older bugs, fixed: `append each x from <list> to <dest>` no longer has
its destination eaten by range parsing — a list source appends the list
(`[1, 2, 3]`), a range still appends the range; `append <expression> to
<list>` parses full arithmetic, so appending `i multiply i` in a loop works
(`[1, 4, 9, 16, 25]`); and a timer's `start time` and `end time` now parse
through the reserved `time` keyword, so they return unix timestamps as
documented.
