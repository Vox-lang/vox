## #103 — fix

`src/analyzer/things.rs:405-448` (`load_things`'s field loop). Support is
now decided **before** the default is even considered: `v1_field_type_
supported` is checked first, and an unsupported type reports only the
"cannot hold yet" error and `continue`s past the default check entirely.
Previously the default-mismatch check ran first and had no arm for an
unsupported type in `default_matches_field_type` — it always answered
`false` there, so an unsupported type's default was reported as "mismatched"
even when it wasn't, rendering both slots of "expected X, got Y" as the
same word.

A field whose type IS supported still gets the default-mismatch error when
its literal default doesn't match — that check is unchanged, only reordered
to run after the support gate. Pinned by `tests/compile_fail/274`.

## #104 — fix

`src/analyzer/scope.rs`'s `check_loop_collection`. The caret now anchors on
the loop clause's own use of the collection instead of the collection's
textually-first mention. Concretely: it builds a construct-specific search
pattern (`from {symbol}` for `each ... from`, or `in {symbol}` for the
older `For each ... in ...,` spelling — both parse to the same
`Statement::ForEach` AST node, so both were fixed; when the collection has
no name of its own, the loop variable is searched instead, via `each
{variable} from`/`each {variable} in`), resolves it with the existing
`find_bind_site_location` helper, and reports through
`push_error_with_hint_at` (which takes an already-resolved location)
instead of `push_error_with_hint` (which searches for the bare symbol's
first textual occurrence — the declaration, in this repro).

`push_error_with_hint` itself is untouched, so every other caller of it is
unaffected — this is the only call site that stopped using it. Message and
hint text are byte-identical to before.

## Temptation resisted

- #103's register entry explicitly wants every standard type (starting
  with `text`) to become a legal thing field, pending verification that
  copying a text handle can't observe mutation. Did not touch
  `v1_field_type_supported`'s allowed-type set — that is the owner's
  design ruling to make, not a diagnostic fix.
- #104's register entry wants a byte/octet iteration form over a buffer
  (`each byte of <buffer>` etc.) so the misanchor case becomes rare by
  construction. Did not add any new loop form or touch the parser's
  `try_parse_each_from` — out of scope, waits for the owner.

The corpus harness (`compile_fail_corpus_reports_errors`) only asserts
that expected substrings are *present*, not that anything else is
*absent* — it can't by itself prove "exactly one error." Added
`tests/bugs_found_103_field_type_single_error.rs` (2 tests, spawns the
compiled binary) to assert that directly:
- `rejected_field_type_reports_exactly_one_error` — asserts exactly one
  `error:` in stderr for the #103 repro, that it's the "cannot hold yet"
  one, and that the garbled "but its default is" template is **absent**.
- `mismatched_default_on_a_supported_type_still_errors` — same exactly-
  one-error assertion for the supported-type-mismatch pin.

(Note for whoever reads this next: `CompileError`'s `Display` wraps
`error` and `hint` in ANSI color codes that split the label from its
trailing colon — e.g. the literal byte sequence is `error<reset>:`, never
a contiguous `"error:"`. A raw `.contains("error:")` or `.contains("hint:
")` is silently always false. Existing `.err` fixtures dodge this by never
including the label, only the hint's content (see `098_foreach_over_map
.err`); the new Rust integration test strips ANSI escapes explicitly
before counting.)
